# DokanTools — M0-01 Remediation Design R1

**Status:** Design proposal only — implementation not approved  
**Baseline:** `efa7d5da139030c092089831f813df697eaed71e`  
**Scope:** Memo-generated customer due vs. manual baki-entry duplication  
**Decision requested:** CH-1 approval before implementation; CH-4 independent design review

## 1. Problem statement (verified from baseline source)

The current `create_memo_transaction` RPC inserts a `baki_entries` row with `type='due'` when a memo has a due amount. The Baki UI also supports standalone due/paid entries. The current ledger row does not carry a source discriminator or memo reference, so the application cannot reliably distinguish:
- receivable already generated by a memo;
- a separate manual receivable;
- a payment/settlement against an existing receivable.

A second manual due row can therefore represent the same real-world memo obligation. Customer + amount + date/note matching is not a safe identity key: legitimate separate sales may have the same customer and amount.

## 2. Design principles

1. Do not use customer/amount/date/note fuzzy matching as a uniqueness key.
2. Preserve genuine manual dues and payments.
3. Keep memo creation, stock deduction, and memo-linked due insertion atomic in the existing memo RPC.
4. Preserve ledger history. No destructive deduplication or silent edits.
5. Use immutable/additive migration(s); do not edit historical migration files.
6. Treat a memo's source identity—not amount or display text—as the identity of a memo-derived receivable.
7. Prevent tenant/customer/memo cross-linking at database level, not only in React/UI.
8. Never claim PostgreSQL concurrency, migration replay, or RLS behavior is verified until run on a disposable staging DB.

## 3. Proposed data model

Add to `public.baki_entries`:

- `source_type text not null default 'manual'`, constrained to `manual`, `memo_due`, `payment` (confirm whether existing `type='paid'` should map to `payment`; do not conflate business direction and origin without a migration plan).
- `source_memo_id uuid null`, populated only for memo-derived due rows.
- Optional `source_operation_id uuid null` only if it adds meaningful audit/idempotency semantics; the existing transaction request operation ID may be reused in audit, but it must not become a second competing business identity.

Required constraints/indexes:
- A memo-derived row must have a non-null memo ID; non-memo rows must have null memo ID.
- Unique partial index on `(shop_id, source_memo_id)` for `source_type='memo_due'` to guarantee at most one memo-due ledger row per memo.
- Composite unique keys/FKs to ensure the linked memo belongs to the same shop and the linked customer belongs to that same shop. Verify PostgreSQL's nullable composite-FK behavior and add explicit RPC validation for memo/customer equality.
- Keep the existing `baki_entries.shop_id` and `customer_id` data model compatible; do not add a FK that makes valid customerless memo sales impossible when `due_amount=0`.

### Legacy backfill

- Existing memo-generated rows can be identified only when the migration can confidently map their `note`/audit metadata to a memo ID. The current memo RPC uses note text `মেমো #<first 8 chars>`, which is not a safe unique join by itself.
- Backfill only rows with an unambiguous full memo identity from trustworthy persisted audit data; otherwise leave them as legacy/manual and produce a reconciliation report.
- Do not auto-delete or merge rows. Record unresolved candidate duplicates for human review.
- The migration must fail or stop with a clear diagnostic if an intended uniqueness constraint would be violated; do not silently pick a winner.

## 4. RPC and application behavior

### 4.1 Memo transaction RPC

- Continue inserting the memo-linked due in the same transaction as memo and stock writes.
- Insert the ledger row with `source_type='memo_due'`, `source_memo_id=<new memo UUID>`, and the same shop/customer IDs.
- The unique memo-source index is the final concurrency guard.
- On idempotent memo retry, return the already completed memo; do not create a second due row.
- Any conflict or invariant failure rolls back the entire memo RPC (memo, stock, ledger, audit and transaction request claim).

### 4.2 Baki UI and RPC

The Baki “বাকি যোগ” flow must distinguish:
- **Memo থেকে বাকি:** select a saved memo with outstanding due. This is not a new due insert. It should show the memo’s existing due ledger record and link/open the memo. If the memo due is already represented, block posting and explain that it was recorded with the memo.
- **ম্যানুয়াল বাকি:** user explicitly confirms it is a separate transaction not already represented by a memo; create a manual due with a stable request ID and source `manual`.
- **জমা/পরিশোধ:** keep as a payment entry with stable request ID. Do not implement memo-specific payment allocation in M0-01 unless required for correctness; clearly label current customer-level aggregate behavior and prevent overpayment against the aggregate balance.

A memo-derived due must never be recreated by a “manual” retry. The UI should offer a memo-linked action rather than free-form re-entry for memo dues. The RPC must enforce memo linkage when a memo reference is supplied.

### 4.3 Business-level duplicate limitation

No database can reliably infer that an unreferenced manual due is “the same business obligation” merely from matching customer, amount, date, item text, or note. Therefore:
- source identity must be explicit;
- the workflow must require users to choose the memo for memo-derived dues;
- manual due remains available for genuine standalone credit;
- acceptance must include a UX warning and audit trail for explicit manual classification;
- residual risk of a user intentionally/mistakenly classifying a memo obligation as unrelated manual credit must be documented, not falsely described as fully prevented.

## 5. Payment allocation / accounting semantics

M0-01 should not silently claim invoice-level settlement. Existing payment entries are customer-level aggregate payments unless there is an explicit allocation table/RPC. A payment must not be represented as a memo-linked due. If memo-level balances are required later, add a separate allocation model (e.g. payment-to-memo allocations) with transactional constraints and audit events; keep it out of this patch unless CH-1 expands scope.

The customer balance remains the sum of ledger debits/credits under the established sign convention. Define and test the sign convention before changing it.

## 6. Cancellation, void and reversal

- Do not hard-delete a memo or memo-derived due after financial posting.
- Cancellation/void should be an audited reversal workflow: append reversal entries/events, retain the original memo and source row, and mark the memo state only if a state field and allowed transitions are designed.
- A unique memo-source constraint must not prevent a legitimate reversal; reversal rows should have their own source/event identity and explicit reference to the original row, not overwrite the original memo-due row.
- Scope of memo cancellation/reversal is **not included** in this remediation unless CH-1 approves it separately. Until then, document that memo cancellation is unsupported and do not offer a destructive UI action.

## 7. Catalog vs. stock RPC partial-success behavior

If item/catalog creation and stock creation are separate calls, a catalog record may remain when stock RPC fails. This is not automatically a financial inconsistency, but UI must report partial success accurately:
- distinguish “catalog item created” from “stock item/quantity created”;
- retry stock using the same request ID and exact payload;
- do not blindly repeat catalog insertion;
- offer safe recovery/verification.
Do not combine unrelated catalog and stock operations into one transaction without checking existing schema and intended workflow.

## 8. Migration plan

1. Add a new timestamped migration after `20261102_p0_idempotency.sql`; never modify prior migration files.
2. Inspect exact existing schema, constraints, grants and RLS policies first.
3. Add columns/checks/indexes/FKs in a backward-compatible sequence.
4. Run preflight queries for candidate memo dues and duplicate source references; include a migration report/query for unresolved legacy records.
5. Apply migration to a disposable PostgreSQL/Supabase staging DB only.
6. Validate migration from a clean schema and replay strategy using the project's actual migration mechanism. Do not assume rerunning a non-idempotent migration is supported.
7. Verify RPC grants, `SECURITY DEFINER`, fixed `search_path`, auth identity and ownership checks after modification.
8. Only then prepare a feature branch PR; no production or real shop data.

## 9. Required tests and acceptance criteria

### Schema / migration
- Existing legacy records are preserved; no silent data loss.
- Memo-linked due row has same shop and customer as its memo.
- Wrong-shop memo/customer linkage is rejected.
- Unique partial index prevents two memo_due rows for the same memo under concurrent inserts.
- Migration works against clean staging and existing representative schema; backfill ambiguity is surfaced.

### RPC / idempotency
- Memo with due creates exactly one memo, one due ledger row, expected stock movements, and audit events.
- Same request ID + same payload retry returns same memo and does not duplicate due/stock.
- Same request ID + changed payload fails closed.
- Concurrent duplicate memo request yields one committed operation.
- Direct duplicate memo_due insertion is blocked by DB constraint.
- Failure at any step rolls back memo, due, stock movement and transaction request claim.
- Manual due with independent request ID and no memo source remains allowed.
- Payment entry remains possible and aggregate overpayment is rejected according to current sign/balance rules.
- Payment retries are idempotent.
- Memo due cannot be recreated through memo-linked Baki UI path.
- Two shops cannot read/write each other's memo or ledger rows.

### UI
- Baki user can clearly choose memo-linked vs genuine manual due.
- Memo-linked due already recorded by memo shows existing due; no duplicate posting button.
- Manual due requires explicit confirmation that it is not already included in a memo.
- Partial catalog/stock success is clearly communicated and safely recoverable.
- Error messages do not encourage generating a new operation ID after an ambiguous result.

### Runtime evidence
- Static SQL checks are insufficient.
- Run SQL tests on PostgreSQL/Supabase staging with at least two test tenants.
- Include transaction rollback, permissions, RLS, concurrent calls, migration/backfill and payment/due behavior.
- Record DB version, migration output, test commands, test results and evidence. No “PASS” claim without logs.

## 10. Rollback and operational risk

- Prefer additive schema changes and feature-flag/disable the memo-linked Baki workflow if UI rollout fails.
- Do not drop new columns/indexes or rewrite ledger rows as an automatic rollback after financial data has been written.
- If the migration fails before data writes, stop and restore the staging snapshot; fix forward.
- If new rows exist, rollback must be a reviewed data-preserving forward migration or restore from verified backup—not destructive column removal.
- Before any pilot, verify backup and restore on staging.

## 11. Explicit exclusions

- No payment-to-memo allocation implementation.
- No automatic fuzzy duplicate detection by amount/customer/date.
- No destructive legacy deduplication.
- No production migration or real financial data testing.
- No code implementation until CH-1 approves this design and CH-4 completes independent review.

## 12. Review questions for CH-1 / CH-4

1. Is source_type better represented as separate origin and transaction direction fields? Current `type` already means due/paid, so avoid overloading it.
2. Should the manual Baki RPC require a new explicit “independent transaction” confirmation flag, and how should this be audited?
3. Which audit fields are required for memo void/reversal in a later milestone?
4. Is memo/customer/shop integrity enforceable with existing constraints, or is a schema redesign needed?
5. Does aggregate payment behavior meet M0-01 acceptance, or should payment allocation be a blocking scope item?
