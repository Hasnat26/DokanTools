## 1. Repository facts and design assumptions

The design was prepared against the specified GitHub baseline and R1 in PR #1. Source facts relevant to this proposal:

- \`baki_entries.type\` currently carries transaction direction (\`due\` / \`paid\`); it does not separately identify origin.
- \`create_memo_transaction\` creates a memo, updates stock and inserts a \`baki_entries\` due row for \`due_amount > 0\` within one RPC transaction.
- Memo-created due notes currently use a truncated memo identifier (first eight UUID characters); this is not a safe unique join key for migration.
- \`create_baki_entry\` supports manual due and paid entries.
- The P0 idempotency migration adds \`transaction_requests.payload_json\`; legacy rows can remain NULL when their original request cannot be reconstructed safely. The RPC currently fails closed with \`IDEMPOTENCY_LEGACY_PAYLOAD_UNAVAILABLE\`.
- The memo RPC validates due-bearing memos require a customer. Memo customer is nullable in the underlying memo schema, so a memo with zero due may legitimately have no customer.
- The memo and baki customer writes have separate UI-side customer-creation calls. Those calls can succeed even if a later transaction RPC fails.
- Stock page writes \`item_catalog\` first and then invokes \`create_stock_item\`; the two writes are not atomic in the baseline.
- The SQL source has RLS and SECURITY DEFINER functions. Effective deployed ACL, owner, role membership, search-path safety and RLS behavior require staging catalog/runtime verification.

All legacy financial history is to be preserved. No fuzzy matching, silent deduplication, or inferred reassignment is allowed.

## 2. F-01 — Separate transaction direction from origin

### 2.1 Canonical meaning

Use two independent attributes:

- **Direction**: economic effect on customer balance.
  - \`due\`: increases customer receivable.
  - \`paid\`: decreases customer receivable (customer payment).
- **Origin**: where/how the activity was created.
  - \`memo\`: generated by a DokanTools memo transaction.
  - \`manual\`: explicitly entered as a separate manual transaction.
  - \`legacy_unclassified\`: historical row whose origin cannot be proven from reliable persisted identity.

Do not overload one enum with both meanings. Keep the existing \`type\` as a compatibility alias only during migration; canonical new writes use \`direction\`. The rollout must either:
1. migrate clients/RPCs to \`direction\` and retain a synchronized legacy \`type\` field temporarily, or
2. retain \`type\` as the canonical direction name and add a distinct \`origin\` field.

**Preferred minimum-risk rollout:** retain \`type\` as direction in the database to avoid needless renaming; document it as direction and add \`origin\`. All RPC inputs and API response names must explicitly call it direction in the contract. A physical rename is not necessary for correctness and creates compatibility risk.

### 2.2 Allowed combinations

| direction / existing type | origin | source_memo_id | Meaning | Allowed for new writes? |
|---|---|---|---|---|
| \`due\` | \`memo\` | required | Memo-generated receivable | Yes, only through memo RPC |
| \`due\` | \`manual\` | NULL | Independent manual credit | Yes, through manual due RPC |
| \`paid\` | \`manual\` | NULL | Customer-level aggregate payment | Yes, through payment RPC |
| \`paid\` | \`memo\` | prohibited | Memo-specific payment/allocation | No; allocation out of scope |
| \`due\` / \`paid\` | \`legacy_unclassified\` | NULL | Historical origin not proven | Read/report only; no new writes |

For new writes, constraints must reject:
- unknown direction/origin values;
- \`paid + memo\`;
- \`memo\` origin without memo ID;
- \`manual\` or \`legacy_unclassified\` origin with memo ID;
- any new \`legacy_unclassified\` row;
- due memo row with a null customer;
- negative/zero amount where the current ledger contract requires positive entry amount (entry amount remains positive; direction defines sign).

A legacy origin state is a migration accommodation, not a user-selectable origin.

### 2.3 Manual due identity and residual risk

A manual due must carry:
- \`manual_reference\`: stable external/business document reference (e.g., paper invoice/receipt/delivery challan ID);
- normalized form generated server-side (trim, Unicode normalization policy, case-fold where applicable);
- \`independent_manual_due_confirmed = true\` from UI intent, validated by RPC and recorded in audit event;
- customer/shop and request ID.

Uniqueness should be enforced on \`(shop_id, customer_id, normalized_manual_reference)\` for manual dues, where the reference is nonempty. Do not accept memo UUID, memo display number, or a memo's truncated note as a manual reference. The UI must prompt the user to search the customer's memos first.

The RPC must reject a reference that exactly identifies a known memo (including an explicitly selected memo source); it must not silently convert that transaction to manual.

**Residual limitation:** a person can misclassify a memo debt as independent manual credit and enter a different paper reference. The system cannot semantically prove the underlying debt is identical from customer/amount/date alone. UI confirmation, source-document reference, memo lookup, manager review/exception and audit trail reduce but do not eliminate intentional or mistaken human misclassification. Do not describe this as complete duplicate prevention.

Genuine manual dues remain valid when the obligation originated outside DokanTools or is otherwise independently documented.

## 3. F-02 — Shop/customer/memo referential integrity

### 3.1 Parent keys and nullability

Existing primary keys on \`customers.id\` and \`memos.id\` do not alone prove same-shop or same-customer linkage. Composite FK targets require matching unique keys.

Required parent uniqueness (verify existing constraints before adding; do not duplicate an already equivalent key):

- customers: \`UNIQUE (shop_id, id)\`
- memos: \`UNIQUE (id, shop_id, customer_id)\`

Because memo customer is nullable, a memo-derived receivable must have a non-null customer. For \`due_amount > 0\`, RPC validation rejects \`p_customer_id IS NULL\`; zero-due/customerless memo is permitted. A composite FK containing nullable \`customer_id\` can bypass enforcement under PostgreSQL's default MATCH SIMPLE semantics; therefore the memo-due path must be non-null by constraint/check and RPC validation, not by assuming the FK handles NULL.

### 3.2 Required ledger constraints

For new memo-origin due rows:

- \`baki_entries.shop_id\` and \`customer_id\` are NOT NULL.
- \`origin='memo'\` implies \`direction='due'\`, \`source_memo_id IS NOT NULL\`, \`customer_id IS NOT NULL\`.
- Composite FK \`(shop_id, customer_id) → customers(shop_id, id)\`.
- Composite FK \`(source_memo_id, shop_id, customer_id) → memos(id, shop_id, customer_id)\`.
- FK delete behavior is RESTRICT/NO ACTION for financial history; no cascading delete of memo/customer/ledger rows.
- Memo source uniqueness: one memo-origin due row per memo, including after reversal/void (reversal implementation is future scope; original identity remains reserved).
- A unique partial index on \`source_memo_id\` for \`origin='memo' AND direction='due'\` prevents multiple memo due rows. This index does **not** prevent manual-origin duplicates and must never be represented as doing so.
- Manual-reference unique key applies only to manual dues; payments are not obligation references.

### 3.3 Same-shop integrity beyond FKs

All RPCs must validate:
- authenticated user owns the shop;
- customer belongs to supplied shop;
- memo belongs to supplied shop;
- memo customer equals supplied ledger customer for memo-origin due;
- source memo is a posted/eligible memo and is not voided;
- referenced stock item belongs to the same shop.

RLS is defense in depth; composite FKs and RPC checks remain required because SECURITY DEFINER functions may bypass RLS depending on owner.

## 4. F-03 — Legacy classification and migration safety

### 4.1 Deterministic classification

Migration classification must be based only on trustworthy persisted identity:

1. Existing \`baki_entries.type\` (\`due\`/\`paid\`) determines direction if valid.
2. Memo origin may be assigned only when a persisted full memo UUID or an equivalent immutable source FK/identity is present and uniquely verified, with matching shop and customer.
3. Existing baseline memo notes such as \`মেমো #<first 8 UUID chars>\` are **not** deterministic identity; do not use them to auto-link.
4. Transaction request payloads can support identity only when the relationship to the actual ledger row is explicit and complete. Payload contents alone do not prove that an arbitrary ledger row is the memo due row.
5. Legacy payments remain \`legacy_unclassified\` unless the origin is provable. Do not classify every historical payment as manual by assumption.

Unclassified rows retain their current amounts, IDs, shop/customer IDs, notes and created timestamps. They remain visible in aggregate balance calculations under existing direction semantics but do not become memo-level settlement claims.

### 4.2 Migration preflight checks

Preflight must report, not silently repair:
- invalid \`type\` values;
- null/invalid shop or customer;
- customer/shop mismatch;
- memo/shop/customer mismatch for any candidate link;
- duplicate candidate memo-source ledger rows;
- duplicate normalized manual references (only if references are already available);
- existing request ID conflicts or incomplete payloads;
- transaction request records in \`processing\` state;
- stock/catalog duplicate or normalized-name conflicts relevant to stock migration;
- parent composite unique-key creation failures;
- dependent views, triggers, grants, policies and RPC signature dependencies.

If preflight finds a conflict that prevents a constraint, migration stops with a diagnostic and preserves rows. No winner is selected automatically.

### 4.3 Legacy request semantics

- Completed legacy request with NULL \`payload_json\`: return \`LEGACY_PAYLOAD_UNAVAILABLE\`; do not re-execute or infer a payload.
- Same request ID + complete canonical payload equal to stored payload: return canonical prior entity/result; no second ledger/stock/audit effect.
- Same request ID + changed payload: reject with payload mismatch.
- Request ID used for a different operation type: reject.
- \`processing\` row with no committed entity: do not blindly re-run. Verify transaction state and resolve using a recovery/administrative path.
- Do not automatically mint a new request ID after a timeout. Client must query/retry with the original ID.
- If migration/backfill cannot prove whether a legacy memo due already exists, the retry must not create another due row. It must fail closed and instruct operator to inspect the saved memo and ledger.

### 4.4 Fresh install, baseline upgrade and interrupted migration

- **Fresh install:** update \`supabase/schema.sql\` so new schema/RPC definitions and grants are consistent with the forward migration.
- **Existing baseline:** add a new forward migration after \`20261102_p0_idempotency.sql\`; never rewrite already-applied migration history.
- **Interrupted migration:** use transactional DDL where PostgreSQL supports it. Do not use nontransactional concurrent index creation in the same migration transaction. If concurrent index build is required, split it into a separately documented, resumable operation with explicit invalid-index detection/cleanup approved by CH-1/CH-3.
- Use a migration ledger/checkpoint only where project migration tooling supports it; do not invent idempotency by blindly wrapping every statement in \`IF NOT EXISTS\` if that could hide a mismatched object definition.
- Recovery: inspect migration history, object definitions and \`pg_index.indisvalid\`; restore a staging snapshot or apply a reviewed forward repair. Do not re-run a partially applied script blindly.
- Run against disposable staging first. Migration execution and rollback are NOT TESTED until runtime evidence exists.

## 5. F-04 — RPC atomicity, idempotency and canonical IDs

### 5.1 Transaction boundary

Memo sale remains one PostgreSQL transaction covering:
- transaction request claim;
- memo insertion;
- stock row locks and quantity updates;
- stock movements;
- memo-origin due row;
- audit events;
- transaction request completion and canonical entity IDs.

Any failure before commit must roll back all of these. A failed transaction must not leave a completed idempotency row or partial memo/stock/due state.

Manual due/payment RPC transaction includes:
- request claim;
- shop/customer validation and lock;
- balance check (for payment);
- ledger row;
- audit event;
- request completion.

Catalog creation remains a separate nonfinancial action unless a future combined catalog+stock RPC is approved. Its partial-success state is defined in §8.

### 5.2 Canonical request payload

Each RPC must define an immutable canonical payload:
- operation type;
- shop ID;
- customer ID (if relevant);
- normalized amount/direction/origin;
- memo ID or manual reference as applicable;
- item lines and normalized business fields;
- reason/metadata that changes business outcome.

Canonicalization must be server-side. Exclude transient UI values that do not affect business semantics. Document rounding, JSON ordering/normalization and null-vs-omitted behavior.

### 5.3 Idempotency behavior

- Stable \`request_id\` is mandatory for all financial writes and stock operations.
- Unique key remains \`(shop_id, operation_id)\`; operation type must also match.
- Same ID + same payload returns prior canonical entity ID and result with duplicate/replay indicator.
- Same ID + changed payload returns a controlled mismatch error; it must not mutate existing data.
- Same ID + another operation type returns conflict.
- A lost response after commit is recovered by same ID and exact payload.
- New request ID is allowed only for a genuinely new business operation, not a retry.
- For completed legacy request with no reconstructable payload, fail closed with explicit \`LEGACY_PAYLOAD_UNAVAILABLE\`; user verifies existing record, and no write is repeated.
- Audit must record original request ID and canonical entity ID. Idempotent retry must not create a second financial audit event; optionally emit a nonfinancial retry-observed event without duplicate accounting impact.

### 5.4 Canonical IDs

RPCs return:
- \`result_entity_id\`: original memo, ledger entry, stock item, or adjustment entity ID;
- \`result_operation_id\`: request UUID;
- \`was_duplicate\`: boolean;
- stable result fields (e.g. balance after commit only if the API guarantees it is a persisted snapshot).

Never return a new synthetic ID on retry. The client must not infer success from a toast; it should refresh/read the canonical entity after uncertain response.

## 6. F-05 — Customer balance and payment concurrency

### 6.1 Aggregate balance invariant

M0-01 supports **customer-level aggregate payments only**; memo-level allocation is explicitly out of scope.

For a shop/customer:

\`aggregate_due = SUM(due entries) - SUM(paid entries) - SUM(reversal credits, if future-approved)\`

Only posted ledger entries contribute. Legacy rows contribute according to their existing \`type\`/direction. No memo-specific outstanding amount is calculated from unallocated payments.

Invariant for new payments:

- payment amount > 0;
- customer and shop valid;
- payment <= current aggregate balance immediately before commit;
- balance is recalculated after acquiring the concurrency lock;
- no overpayment caused by simultaneous RPC requests;
- all writers affecting this aggregate use the same lock protocol; direct table writes are denied.

### 6.2 Lock protocol

For this pilot, retain/standardize the existing shop-row lock protocol to reduce risk of changing concurrency semantics, then lock the customer row where applicable. Every RPC affecting the same customer's aggregate balance must use the same lock order:

1. verify auth and shop ownership; lock shop row;
2. lock customer row in that shop;
3. compute current committed balance;
4. validate amount;
5. insert payment/due and audit;
6. complete request;
7. commit.

Lock order must be consistent across memo due, manual due, payment and future adjustments. The shop-level lock is conservative and serializes financial operations within a shop; it may limit throughput but is acceptable for a controlled small-shop pilot until profiling supports finer-grained locking. Do not allow an alternate write path to bypass the lock.

### 6.3 Concurrent payment example

Starting balance = 100. Two sessions submit 70 each with different request IDs:
- Session A acquires locks, reads 100, writes payment 70, commits; balance becomes 30.
- Session B waits, then reads 30; payment 70 is rejected.
- Final balance = 30, total accepted payment = 70, never negative.

Two sessions with the **same** request ID and payload:
- exactly one financial row commits;
- other returns the same canonical payment ID as duplicate.

Payment allocation to memo IDs, FIFO/LIFO, per-invoice settlement and memo-level outstanding balances remain out of scope.

## 7. F-06 — Preserve genuine manual dues and payments

- Manual due remains a supported transaction with \`direction='due'\`, \`origin='manual'\`.
- Manual payment remains supported with \`direction='paid'\`, \`origin='manual'\`.
- Manual due requires a customer, amount, business reference, stable request ID and explicit independent-transaction confirmation.
- Manual payment is a customer aggregate payment; no memo reference or settlement claim.
- UI must show a warning/confirmation: “This due is independent of any memo already recorded in DokanTools.”
- RPC records actor, shop, customer, request ID, origin, direction, source reference, confirmation and timestamp in audit metadata.
- Client cannot choose \`origin='memo'\` or write memo source IDs through direct table operations.
- A manual due with same customer and amount as a memo is not automatically rejected merely for matching amount; this would block legitimate repeat transactions. Instead, memo search/source reference and human confirmation are required.
- If a known memo is selected as source, RPC routes to existing memo due or rejects duplicate; it must not create a manual due row for it.
- Human misclassification risk remains and must be disclosed in pilot acceptance.

## 8. F-07 — Memo cancellation/reversal is excluded from M0-01

### 8.1 Current restrictions

- No posted memo cancellation/void UI or RPC may be introduced in M0-01.
- No hard-delete of posted memo, due row, payment, or stock movement.
- Financial fields of posted memos are immutable through existing/new authorized paths.
- If current UI exposes edit/delete paths, they must be blocked or explicitly identified as a separate prerequisite; this design does not authorize destructive changes.
- M0-01 must not claim to support memo cancellation or receivable reversal.

### 8.2 Future reversal requirements

Future work must define:
- reversal reason, actor, timestamp and operation ID;
- original memo/ledger/stock movement links;
- atomic reversal of memo receivable and stock effects;
- payment-before-cancel policy;
- audit retention and no deletion;
- idempotent void/reversal;
- index/source identity reservation after reversal;
- correction/reissue with a new memo ID;
- accounting sign-off and test coverage.

A reversed memo's source identity should remain reserved; reversal must not permit re-creating a second due for the same original memo.

## 9. F-08 — Catalog/stock operation IDs and recovery

### 9.1 Separate business operations

The existing UI has a catalog upsert followed by stock RPC. Treat these as distinct operations unless the future combined RPC is approved:

- \`catalog_operation_id\`: stable ID for catalog add/update.
- \`stock_operation_id\`: stable ID for stock item creation/opening stock.
- \`stock_request_id\`: the same ID reused for all retries of the same stock RPC.

If stock creation is retried after catalog write, do not repeat catalog insertion blindly.

### 9.2 States and user messages

| State | Meaning | UI/action |
|---|---|---|
| \`catalog_only\` | Catalog record intentionally exists without inventory | Valid state; label “Catalog only / Not stocked” |
| \`catalog_saved_stock_pending\` | Catalog save succeeded; stock result is failed/unknown | Show partial result; keep request ID and offer verify/retry |
| \`stock_created\` | Stock RPC committed and canonical stock ID known | Display inventory item |
| \`stock_result_unknown\` | Network response lost; commit status unknown | Read transaction request by same ID; retry same ID only |
| \`stock_failed\` | RPC definitively rolled back/failed | Preserve catalog; allow safe retry with same ID/payload |

### 9.3 Recovery rules

- Retry stock RPC with same ID and exact payload.
- If request is completed, return canonical stock item ID; do not duplicate opening stock movement.
- If no completed request exists and no stock entity was committed, retry may proceed.
- If request is processing/unknown, verify DB state before new request ID.
- Catalog-only products must not be included in inventory quantity, stock deduction or valuation.
- UI must never show “Product and stock saved” unless both states are confirmed.
- A future atomic \`create_catalog_and_stock_item\` RPC may eliminate partial state, but it must preserve intentional catalog-only workflow and be separately designed/tested.

## 10. F-09 — RPC privilege, SECURITY DEFINER, RLS and tenant isolation

### 10.1 Privilege matrix (target; verify effective ACL in staging)

| Operation | anon | authenticated direct table write | authenticated RPC | service/admin |
|---|---|---|---|---|
| Read own permitted shop/customer/memo/stock | Deny except narrow public published views | N/A | N/A | Explicit operational access only |
| Insert/update memo | Deny | Deny | \`create_memo_transaction\` only | No routine bypass |
| Insert/update baki ledger | Deny | Deny | due/payment RPCs only | Break-glass with audit |
| Insert/update stock quantity/movements | Deny | Deny | stock creation/adjustment/memo RPC | Break-glass with audit |
| Write transaction_requests/audit_events | Deny | Deny | RPC only | Break-glass with audit |
| Read own ledger/stock | Deny unless existing policy permits authenticated read | Read governed by RLS | N/A | Explicit |
| Public shop/products | Narrow published projection only | N/A | Public read only | Explicit |

### 10.2 Function hardening requirements

For every SECURITY DEFINER RPC:
- fixed safe \`search_path\` (prefer \`pg_catalog, public\` or fully qualified objects plus pg_catalog; verify no untrusted schema is writable by caller);
- explicit \`auth.uid()\` and shop-owner checks;
- function owner is a controlled non-login role/owner with only required privileges;
- revoke EXECUTE from \`PUBLIC\`, \`anon\`, and any unintended role;
- grant EXECUTE only to \`authenticated\` where intended;
- restate grants/revokes in the forward migration after \`CREATE OR REPLACE FUNCTION\`;
- check overloads: revoke/grant on exact function signatures;
- no caller-controlled dynamic SQL;
- explicit tenant predicates even if RLS exists;
- no direct table write grant to browser role for protected financial tables;
- verify role memberships, owner, \`BYPASSRLS\`, ACLs and effective privileges using PostgreSQL catalog queries.

Do not assume replacing a function re-applies intended ACL policy; do not infer ACL from migration source alone.

### 10.3 RLS and tenant integrity

- RLS enabled on all tenant-owned financial/inventory tables.
- Policies require shop ownership from authenticated identity.
- Cross-shop joins/foreign keys are prevented by composite shop/customer/memo FKs, not RLS alone.
- SECURITY DEFINER functions must not accidentally bypass tenant predicates.
- Test authenticated tenant A attempting to select/update/delete tenant B rows and invoking RPC with B's shop/customer/memo IDs.
- Test anon/public access to customer ledger, memo and inventory details.
- Test direct insert/update/delete against protected financial tables returns permission denied.
- Runtime RLS/ACL status remains **NOT TESTED** until staged.

## 12. Acceptance criteria

M0-01 remains **NO-GO** unless all mandatory criteria are satisfied:

1. Direction/origin combination constraints reject invalid rows.
2. One memo-origin due per memo enforced under concurrent calls.
3. Same-shop/customer/memo integrity enforced by composite keys/FKs and RPC validation.
4. Memo due requires non-null customer; zero-due customerless memo remains valid.
5. Manual credit and customer-level payments remain functional and auditable.
6. Manual reference duplicates are prevented; human misclassification limitation is documented in UX and pilot training.
7. Legacy rows preserved; ambiguous records remain unclassified; migration reports preflight conflicts.
8. Same-ID/same-payload retries return canonical IDs and have one committed effect.
9. Changed payload and legacy NULL-payload retries fail closed.
10. Concurrent payments cannot overpay aggregate balance.
11. Memo/payment allocation is not falsely represented; per-memo outstanding is not displayed as settled.
12. Posted memo cancellation/delete/edit financial fields are blocked in this scope.
13. Catalog-only and partial catalog/stock states are accurately presented and safely retried.
14. Direct writes to protected tables denied; RPC grants/revokes and SECURITY DEFINER owner/search path verified.
15. Tenant A cannot read/write Tenant B data through RLS, RPCs, direct access, or FK relationships.
16. Fresh install, baseline upgrade, migration interruption/recovery pass on staging.
17. T01–T27 pass with actual PostgreSQL/Supabase runtime evidence and two independent tenants.
18. Backup and restore drill succeeds on staging before any pilot.

Static tests and code inspection do not satisfy runtime acceptance.

## 13. Rollback and recovery

- No production changes are authorized.
- Snapshot staging before migration and verify restore.
- If migration fails before financial writes: stop, inspect migration state and restore staging snapshot or apply reviewed forward repair.
- If new financial rows have been written: do not drop new columns/indexes or delete ledger rows to roll back. Use a reviewed forward correction or restore a verified backup with explicit data-loss acknowledgement.
- Application rollback does not automatically rollback database schema or financial effects.
- If balance, tenant isolation, idempotency or migration integrity is uncertain: stop staging financial writes and keep pilot NO-GO.
- Never auto-delete duplicate financial entries; reconciliation requires CH-1 accounting review and append-only adjustment/reversal (future feature).
